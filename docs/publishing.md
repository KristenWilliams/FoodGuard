# GitHub 发布与后续安排

## 本次发布范围

- 源码：当前 Android、前端、轻量后端、共享规则、公开图像/字体、构建配置和文档。
- 不公开：真实 Key、本机 `.env*`、SSH 和签名私钥、SDK 路径、私人测试照片、用户历史、运行日志、旧 APK。
- Release：`v1.2.2-preview`，标记 **Pre-release**，附件 `FoodGuard-1.2.2-preview.apk` 和 `SHA256SUMS.txt`。调试签名测试包，不作为商店正式发行。
- 介绍：[中文 README](../README.md)、[English README](../README.en.md)。GitHub About 文案、网址和主题在 [github-about.json](github-about.json)。网址指向 Releases，不把 API 根路径当网页版应用。
- 软件许可证待维护者确认；第三方字体许可已保留。没有根目录 `LICENSE` 时，只公开源码不等于授予开源许可。

## 发布步骤

1. 审查准备提交的文件及历史，运行密钥扫描、检查、测试、Android 构建与 APK 扫描。没有匹配不代表完整安全审计。
2. 与 GitHub 最新 `main` 对齐，保留远端已有修复。不强推或删除远端提交。
3. 推送源码及版本标签，创建 Pre-release，使用 [本版说明](releases/v1.2.2-preview.md)。只上传本次审核过的 APK 与校验文件。
4. 更新 About；读回提交、README、Release 附件和介绍，核对下载文件 SHA-256。推送成功不等于 Release 已发布，草稿也不是公开发行。

这些步骤需要仓库写权限。API/工具只能读取时，先恢复授权，不反复上传、伪称已发布或请求用户在聊天里提供凭证。GitHub Actions 的检查工作流不会自动创建 Release，避免把每次重新生成调试签名的构建当升级包。

## Codex 可以继续完成

- 获得正确授权后推送、上传 Release、设置 About、读回验证；根据维护者选择加入许可证。
- 修复 CI 或试用反馈，建立真实标签验证用例、真机和大陆网络测试清单；不将生成图当准确率证据。
- 为正式发行配置私有 release 签名、构建更新流程和版本规则；签名私钥不进入 GitHub。
- 在单独授权后检查 FoodGuard 的服务器容量、代理隐私、防滥用和发布运维；本次不改 VPS 或 Nginx。

## 维护者需要决定或参与

1. **授权**：使用对 `KristenWilliams/FoodGuard` 有写权限的 GitHub 登录/连接。About 修改通常还需仓库管理权限。不在聊天中粘贴 GitHub Token 或密码。
2. **许可证**：决定是否采用 MIT 等开源许可证。代码可以开源、AI 额度可以单独出售；许可证不自动授予第三方素材权利，Key 售卖/支付功能目前也未实现。
3. **正式签名**：正式发布前决定签名持有方式，私钥及密码必须自行安全备份。当前测试包转正式签名不能直接覆盖升级，需要规划本机数据迁移。
4. **真实试用**：提供有授权、已脱敏的真实食品标签并参与至少几台真机/大陆网络试用。无需提供私人照片或用户历史。
5. **商业发行**：确认图像资产使用权、服务责任和商店/隐私合规；审核任何曾公开或分享的 Key，必要时在上游撤销。需要售卖额度时，再决定限额、到期、撤销和结算规则。

日常编码、打包、文档和排错不需要维护者自行处理。账号授权、许可证、签名保管与商业决定不能由自动化代替。
